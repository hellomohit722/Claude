# 1. What is Prompt Engineering?

**Prompt engineering** is the practice of designing instructions and providing context so that an AI model can perform a task more effectively and consistently.

Think of it like programming.

### Traditional programming

```text
Input
  ↓
Code
  ↓
Output
```

### Prompt-based interaction

```text
Input
  ↓
Instructions + Context + Constraints
  ↓
LLM
  ↓
Output
```

An LLM is probabilistic, so the way we specify a task can significantly affect the response.

---

# 2. The 6-Part Prompt Structure

For many tasks, use this mental model:

```text
ROLE
  ↓
CONTEXT
  ↓
TASK
  ↓
CONSTRAINTS
  ↓
EXAMPLES
  ↓
OUTPUT FORMAT
```

Not every prompt needs all six components.

The goal is not to make every prompt long. The goal is to provide the information the model needs.

---

# 3. ROLE

Tell Claude what perspective, expertise, or behavior you want it to use.

### Weak

```text
Explain Selenium.
```

### Better

```text
You are a senior QA automation engineer
with extensive experience in Selenium and Java.

Explain Selenium.
```

### Why can a role help?

A role can establish:

- Desired expertise level
- Perspective
- Communication style
- Relevant domain context

### Important

A role does **not** magically give Claude new knowledge.

It mainly helps establish the desired perspective and behavior.

---

# 4. CONTEXT

Context tells Claude the information surrounding the task.

### Weak

```text
Fix this code.
```

Claude has very little information.

### Better

```text
I am building a Selenium automation framework
using Java, TestNG and Maven.

The framework uses Page Object Model.

This test is failing during login.

Here is the test:

[code]
```

Now Claude knows:

```text
Technology
+
Architecture
+
Problem
+
Relevant Code
```

This gives the model a better basis for solving the problem.

---

# 5. TASK

Clearly tell Claude what you want it to do.

### Weak

```text
Selenium login.
```

### Better

```text
Create automated test cases for the login functionality
of a web application using Selenium WebDriver,
Java and TestNG.
```

The second prompt contains an explicit action.

### Useful task verbs

```text
Explain
Analyze
Compare
Generate
Debug
Refactor
Review
Summarize
Extract
Classify
Design
Implement
Evaluate
```

Use specific action-oriented verbs.

---

# 6. CONSTRAINTS

Constraints control what Claude should and should not do.

Example:

```text
Constraints:

- Use Java 17.
- Use Selenium 4.
- Use TestNG.
- Follow Page Object Model.
- Do not introduce DTOs.
- Do not use unnecessary design patterns.
- Keep the implementation beginner friendly.
```

Constraints are especially useful in software development because they prevent the model from making unwanted architectural decisions.

For example:

```text
Keep the implementation simple.
Do not introduce unnecessary abstractions.
```

---

# 7. OUTPUT FORMAT

Tell Claude how you want the answer structured.

### Without output format

```text
Analyze this code.
```

### With output format

```text
Analyze this code.

Return the response in this format:

## Problems

- Problem 1
- Problem 2

## Why They Matter

- Explanation

## Recommended Fix

- Fix 1
- Fix 2

## Improved Code

```java
...
```
```

Now you have explicitly defined the expected structure.

# 8. XML Tags

XML-style tags can help clearly separate different parts of a prompt.

```text
<role>
You are a senior Java engineer.
</role>

<context>
I am building a Spring Boot REST API.
</context>

<task>
Review the following controller.
</task>

<constraints>
- Keep the implementation simple.
- Do not introduce DTOs.
- Explain every important change.
</constraints>

<code>
[paste code here]
</code>
```

Think of the tags as clear boundaries between different types of information.

---

# 9. Why XML Tags Can Be Useful

Instead of:

```text
Here is some documentation.

The user wants a refund.

Here is another document.

Analyze the user's request using the documents.
```

Use:

```text
<documents>
...
</documents>

<user_request>
...
</user_request>

<task>
Analyze the request using the documents.
</task>
```

Now Claude can distinguish:

```text
DOCUMENTS
     ↓
USER REQUEST
     ↓
TASK
```

This becomes especially useful with:

- Long documents
- RAG
- Agents
- Tool outputs
- Multiple pieces of context
- Claude API applications

# 10. Few-Shot Prompting

Few-shot prompting means giving the model examples of the desired behavior before asking it to perform the task.

## Zero-shot

```text
Classify this review as Positive or Negative.

Review:
"The product is amazing."
```

No examples are provided.

## Few-shot

```text
Classify reviews as Positive or Negative.

<examples>

<example>
Review: "The product is amazing."
Classification: Positive
</example>

<example>
Review: "The product stopped working after one day."
Classification: Negative
</example>

</examples>

Now classify:

Review:
"The battery life is excellent."
```

Claude can infer the pattern from the examples.

---

# 11. Why Examples Are Powerful

Suppose you want Claude to evaluate candidates.

Weak:

```text
Give candidates a score.
```

Better:

```text
<example>
Candidate:
Strong Java knowledge.
Weak SQL knowledge.
Good problem solving.

Score:
8/10
</example>

<example>
Candidate:
Basic Java knowledge.
Unable to solve coding problem.
Poor communication.

Score:
4/10
</example>
```

Now Claude has examples demonstrating the expected behavior.

# 12. Prompt Chaining

Don't always try to solve a complex problem in one huge prompt.

Instead of:

```text
Analyze this 500-page technical document,
extract requirements,
design architecture,
write code,
generate tests,
and create documentation.
```

Break it into:

```text
Step 1
Extract requirements
       ↓
Step 2
Review requirements
       ↓
Step 3
Design architecture
       ↓
Step 4
Generate implementation
       ↓
Step 5
Generate tests
       ↓
Step 6
Generate documentation
```

This is called **prompt chaining**.

The output of one step can become the input to the next step.

---

# 13. Prompt Chaining Example

### Prompt 1

```text
Analyze this requirement and extract testable scenarios.
```

Output:

```text
Login with valid credentials
Login with invalid credentials
Empty username
Empty password
Locked account
```

### Prompt 2

```text
Convert these scenarios into detailed test cases.
```

### Prompt 3

```text
Convert these test cases into Selenium + TestNG code.
```

### Prompt 4

```text
Review the generated Selenium code for reliability.
```

# 14. Bad Prompt → Good Prompt

## Weak

```text
Create Spring Boot authentication.
```

Claude has to guess:

- Java version
- Spring Boot version
- Database
- Authentication mechanism
- JWT or session authentication
- User roles
- Project structure
- Output expectations

## Stronger

```text
<role>
You are a senior Spring Boot developer.
</role>

<context>
I am learning Spring Boot Security.
I am a beginner with Spring Security.
</context>

<task>
Create a simple JWT authentication system.
</task>

<requirements>
- Java 17
- Spring Boot 3.x
- Spring Security 6
- H2 database
- JWT authentication
- Login and signup
- Two roles: USER and ADMIN
</requirements>

<constraints>
- Keep the implementation beginner friendly.
- Avoid unnecessary DTOs.
- Explain each important class.
- Do not introduce advanced architecture.
</constraints>

<output>
1. Project structure
2. pom.xml dependencies
3. Entity
4. Repository
5. Security configuration
6. Controller
7. JWT implementation
8. Testing instructions
</output>
```

This gives Claude much less room for unwanted assumptions.

# 15. Don't Over-Prompt

A common beginner mistake is:

> "The longer the prompt, the better the answer."

Not necessarily.

The goal is:

> **Give the model the information it needs in a clear structure.**

For a simple task:

```text
Explain ThreadLocal in simple terms with a Java example.
```

may be enough.

For a complex engineering task:

```text
Role
+
Context
+
Requirements
+
Constraints
+
Examples
+
Output Format
```

may be appropriate.

# 17. Prompt Engineering vs Context Engineering

**Prompt engineering** focuses mainly on how we write instructions.

**Context engineering** is broader. It focuses on what information we provide to the model and how we organize, select, retrieve, and present that information.

Think:

```text
Prompt Engineering
        ↓
How do I instruct Claude?

Context Engineering
        ↓
What information should Claude have?
How should I organize it?
What should I retrieve?
What should I leave out?
```

Context engineering becomes increasingly important with:

- Large repositories
- RAG
- Agents
- MCP
- Long documents
- Production AI systems

# 19. Day 2 Key Terms

| Term | Meaning |
|---|---|
| Prompt Engineering | Designing instructions for effective model behavior |
| Role | Defines the desired perspective/expertise |
| Context | Information relevant to the task |
| Task | The action Claude should perform |
| Constraints | Rules or limitations Claude should follow |
| Output Format | Structure expected in the response |
| XML Tags | Structured boundaries used to organize prompt content |
| Few-Shot Prompting | Providing examples before the actual task |
| Zero-Shot Prompting | Asking the task without examples |
| Prompt Chaining | Breaking a complex task into sequential prompting steps |
| Context Engineering | Managing the information available to the model |

# 20. Day 2 Final Takeaway

A strong prompt is not necessarily a long prompt.

The goal is to reduce ambiguity and provide the right information.

```text
              GOOD PROMPT
                   ↓
        ┌──────────┴──────────┐
        ↓                     ↓
   Clear Instructions      Good Context
        ↓                     ↓
      Task                Relevant Data
        ↓                     ↓
   Constraints          Useful Examples
        └──────────┬──────────┘
                   ↓
             Claude / LLM
                   ↓
            Better Output
```

For complex workflows:

```text
Complex Goal
     ↓
Break into steps
     ↓
Prompt 1
     ↓
Output
     ↓
Prompt 2
     ↓
Output
     ↓
Prompt 3
     ↓
Final Result
```
